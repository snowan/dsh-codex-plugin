# DSH rc.7 compatibility report — 2026-08-18

## Result

The hardened plugin stack passes its deterministic gates, live Codex App
Server scenarios, and isolated DeepSeek Harness `0.1.0-rc.7` headless
scenarios. Testing found one rc.7 type-contract change before publication:
DSH replay metadata is now a `ReplayEnvelope` whose adapter-private state is
nested under `response`. The compatibility change preserves the same opaque
Codex replay payload inside that envelope.

## Compatibility finding

The first rc.7 typecheck failed at both successful finish sites because a bare
`ReplayState` no longer satisfies `ReplayEnvelope`. The fixed shape is:

```ts
{
  response: {
    protocol: 'dsh-codex/1',
    bridgeId,
    threadId,
    turnId,
    pendingCallIds,
  },
}
```

Regression assertions cover both a normal stop and a tool-call boundary,
including the pending call id carried in `response`.

## Direct Codex comparison

Codex CLI did not change from the 2026-08-17 comparison, so this compatibility
run did not repeat the single-sample direct timing. The earlier report recorded
functional parity for exact output and workspace package reading, with DSH plus
plugin and direct `codex exec` each faster in one of the two samples. Those
numbers are smoke measurements, not a statistically meaningful benchmark; see
[the initial report](REPORT-2026-08-17.md).

## Remaining external dependency

DSH rc.7 does not yet forward a Session's workspace through published
`GenerateOptions`. The coordinated source change is pushed to
`snowan/deepseek-harness:michi/forward-session-workspace`, but the upstream
repository currently disables creation of pull requests. Until upstream takes
that commit or an equivalent change, the plugin uses its configured `cwd`
fallback on unmodified DSH releases.
